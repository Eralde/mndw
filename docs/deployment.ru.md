# Развёртывание

mndw упаковывается для сетевых устройств в IPK для каждой архитектуры. Пакет содержит
статический хост, встроенные плагины, бинарный файл `mndwd`, помощник определения порта
устройства и init-скрипт.

## Структура устройства

Установленная структура сосредоточена под `/opt`:

```text
/opt/share/www/mndw/                         package-owned host SPA
/opt/share/www/mndw/plugins/                 package-owned built-in plugins
/opt/share/www/mndw/bin/mndw-self-update.sh  self-update helper
/opt/sbin/mndwd                              daemon binary
/opt/etc/init.d/                             daemon init script
/opt/var/lib/mndw/                           selected port, session state, staging
/opt/var/lib/mndw/frontend-port              mndwd's selected browser-facing port
/opt/var/lib/mndw/user-plugins/              durable uploaded user-plugin files
/opt/var/lib/mndw/state.json                 durable plugin metadata and manifests
/opt/var/lib/mndw/legacy/                    preserved legacy 80-mndw.conf files
/opt/tmp/mndw/plugin-runtime/                runtime sockets and leases
/opt/var/mndw/                               self-update lock, intent, pending, rollback
```

Пользовательские плагины хранятся отдельно от встроенных и обслуживаются mndwd через псевдоним
`/user-plugins/`. Каталог состояния не заменяется при обновлении. Старый `80-mndw.conf`
перемещается в `/opt/var/lib/mndw/legacy/` до распаковки нового пакета.

Одобренные файлы пользовательских плагинов — данные времени выполнения, а не файлы под
контролем пакета. При обновлении `preinst` переносит их из старого каталога
`/opt/share/www/mndw/user-plugins/`, поскольку псевдоним mndw обслуживает
`/opt/var/lib/mndw/user-plugins/`. При удалении `postrm` выполняет такую же миграцию перед
удалением старого корня приложения. `/opt/var/lib/mndw`, его `state.json`, staging и файлы
пользовательских плагинов сохраняются при удалении и повторной установке; `purge` не меняет
этот контракт сохранения данных на уровне пакета. Для полной очистки удаляйте плагины через
управление или намеренно удаляйте их постоянные файлы.

## HTTP-сервер

mndwd обслуживает весь браузерный трафик через один слушатель:

- статический SPA и файлы плагинов с запасным вариантом `index.html`;
- псевдоним `/user-plugins/` для постоянных файлов пользовательских плагинов;
- прозрачный прокси устройства для `/rci`, `/ci` и `/auth`;
- маршруты плагинов `/api` и WebSocket с проверкой сессии.

Режим «обслуживать всё» включается через `--frontend-dir`; `--frontend-listen` управляет
адресом привязки и по умолчанию равен IPv4 `0.0.0.0`. При старте mndwd выбирает сохранённый
`frontend-port`, затем старое значение миграции `lighttpd-port`, затем `1189`, а после этого
оставшиеся порты в запасном диапазоне `1190..1289`. Выбранный порт атомарно записывается в
`frontend-port`. Маршрутизация запросов, порты слушателя и upstream-цели определяются в
[`contracts/routing.ru.md`](../contracts/routing.ru.md).

## Размещённый OPKG feed и самообновление

Артефакты размещённого feed публикуются по путям для конкретных архитектур:

```text
https://eralde.github.io/mndw-opkg-feed/aarch64-3.10/
https://eralde.github.io/mndw-opkg-feed/mips-3.4/
https://eralde.github.io/mndw-opkg-feed/mipsel-3.4/
```

Используйте bootstrap размещённого `add_repo.sh`. Он выбирает точную поддерживаемую
архитектуру устройства, устанавливает опубликованный открытый ключ, создаёт
`mndw-feed.conf` только при его отсутствии и выполняет `opkg update` плюс `opkg install mndw`.
Bootstrap не включает `check_signature`, поэтому существующие сторонние feed сохраняют
текущее поведение. Старый `build/packaging/install.sh` работает только с локальным feed и не
должен копироваться в размещённый feed.

Settings → System update использует цели, полученные от сервера. Apply загружает один точный
целевой IPK в `/opt/var/mndw/pending/`, запускает упакованный helper с удерживаемой блокировкой
и устанавливает этот точный путь после перезапуска демона. Revert использует проверенный указатель
`/opt/var/mndw/rollback/version` и нормализованный IPK. Check и apply/revert требуют обычную
сессию управления; POST-запросы требуют `X-Mndw-Csrf: 1`.

## Конвейер IPK

`pnpm build-ipk --arch <arch>` выполняет такую работу:

1. устанавливает зависимости workspace по lock-файлу;
2. собирает хост и общие бандлы;
3. упаковывает встроенные плагины;
4. собирает `mndwd` для выбранной архитектуры;
5. проверяет обязательные файлы staging;
6. создаёт архивы данных и управления ustar с владельцем root;
7. создаёт IPK для конкретной архитектуры.

Карта bare target включает `aarch64`, `mips` и `mipsel`. Поверхности IPK используют
соответственно `aarch64-3.10`, `mips-3.4` и `mipsel-3.4`. `--all` собирает весь набор.
Feed пакетов содержит одну запись для каждой архитектуры.

Архивы примеров, предназначенные для загрузки, создаются отдельно командой
`pnpm build-example-plugins`: по одному архиву для каждого непосредственного каталога примера
с манифестом. Примеры с бэкендом получают по одному архиву с меткой target на каждую цель;
примеры без бэкенда получают один архив. UI может отклонить известный архив target, если
`show.version.arch` указывает другую цель; неизвестные или переименованные архивы сохраняют
обычное поведение загрузки. Загрузка бэкенда требует одобрения до активации; примеры без
бэкенда устанавливаются сразу.

Публикация записи IPK/feed не настраивает архитектуру устройства. Список архитектур opkg и
feed Entware должны содержать соответствующую цель с суффиксом ядра, включая `mips-3.4` для
big-endian MIPS.

## Установка и обновление

`install.sh` настраивает feed, выполняет `opkg update` и устанавливает mndw. Он больше не
записывает политику владения lighttpd. При обновлении со старого HTTP-сервера lighttpd
`postinst` удаляет устаревшие runtime-артефакты mndw, сообщает однократное уведомление,
если старая политика считала lighttpd принадлежащим mndw, затем перезапускает `S70mndwd`.
Неудачный перезапуск сохраняет старое значение `lighttpd-port` для повторной попытки;
успешный перезапуск его использует.

Установка запускает mndwd и сообщает выбранный URL панели после готовности `frontend-port`.
При развёртывании нужно проверить:

1. браузер может подключиться к хосту;
2. аутентификация достигает сетевого устройства;
3. встроенные плагины появляются в списке;
4. загрузка, одобрение и диспетчеризация бэкенда работают.

До запуска mndwd init пакета определяет HTTP-порт сетевого устройства, проверяя `/auth` на
локальных слушателях и наличие аутентификации `x-ndw2-interactive` или `x-ndw4-interactive`.
Если совпадает более одного слушателя, задайте `MNDW_DEVICE_PORT=<port>` в
`/opt/etc/mndw.conf`. Обнаруженный URL передаётся mndwd как `--device-url`; псевдоним
совместимости не поддерживается.

После обновления или удаления/повторной установки проверьте frontend-порт, резервную копию
legacy-файлов, постоянные файлы пользовательских плагинов и `/opt/etc/mndw.conf`. Smoke-тест на реальном
устройстве обязателен, даже если локальные тесты и CI успешны. Выпуск этой миграции также
требует проверки порядка жизненного цикла opkg в целевой Entware и того, что
`/opt/share/www` и `/opt/var/lib` используют одну файловую систему; shell-тесты хоста не
доказывают ни одно из этих условий.

Для диагностики слушателя проверьте выбранный порт, лог mndwd, обнаружение устройства и
активные слушатели:

```sh
cat /opt/var/lib/mndw/frontend-port
grep -a -- '--frontend-dir' /opt/var/log/mndwd.log
sh /opt/share/www/mndw/bin/mndw-device-port.sh detect 192.168.1.1
netstat -lnt 2>/dev/null
```

## Граница безопасности

Демон — граница безопасности для исполняемых возможностей плагинов. В production:

- управление требует действующую сессию роутера;
- загруженные плагины с бэкендом проходят staging до одобрения;
- доступ к HTTP/WebSocket-маршрутам контролируется одобрением и статусом включения;
- публичный доступ к маршрутам явно указывается и виден при проверке;
- размер запросов, время выполнения и параллелизм ограничены;
- одобренные команды и дочерние service выполняются с привилегиями устройства демона.

Сервис требует аутентификацию для загрузки, одобрения и выполнения shell; небезопасные изменения
управления также требуют `X-Mndw-Csrf: 1`. `--dev` намеренно обходит проверки сессии, но не
обходит это требование CSRF, поэтому не должен использоваться в production.

## Проверка в окружении, похожем на устройство

Блокирующая цель CI — обычный контейнер Alpine с BusyBox `/bin/sh`, демоном, собранным для
Linux amd64, и заглушкой opkg. Это обнаруживает shell-скрипты, которые работают в shell
разработки, но ломаются в shell, похожем на роутер.

Необязательный harness Entware проверяет реальную установку opkg, когда меняется управление
зависимостями. Он не блокирует сборку, поскольку загружает внешний тулчейн и feed.
