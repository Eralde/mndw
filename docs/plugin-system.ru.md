# Система плагинов

Плагины mndw — независимо упакованные UI-модули с явным манифестом. Хост предоставляет
UI-сервисы, а `mndwd` — контролируемое выполнение бэкендов. SDK — контракт, общий для хоста,
CLI и авторов плагинов.

## Устройство плагина

Архив плагина содержит манифест, точку входа фронтенда и необязательные ресурсы бэкенда:

```text
manifest.json
index.js
index.css                 optional
mndw.lock.json            generated by mndw pack
backend/
  main.sh                 optional
```

Точка входа экспортирует `createInstance`:

```ts
export function createInstance(
  container: HTMLElement,
  context: PluginContext,
): PluginInstance | Promise<PluginInstance>
```

Экземпляр обязан предоставлять `unmount`. Он может предоставлять `onResize`, получающий
текущие ширину и высоту в единицах сетки.

## Контракт манифеста

Каждый манифест содержит `manifestVersion: 1`, безопасное для пути имя, семантическую версию,
тип `widget` или `page`, подпись `label` и безопасный относительный путь точки входа.

Виджеты объявляют размеры в единицах сетки:

```json
{
  "manifestVersion": 1,
  "name": "traffic-widget",
  "version": "1.0.0",
  "type": "widget",
  "label": "Traffic",
  "entry": "index.js",
  "size": { "w": 4, "h": 3, "minW": 2, "minH": 2 }
}
```

Страницы объявляют маршрут из одного сегмента, например `/traffic`. `/`, `/login` и `/settings`
зарезервированы; хост также резервирует `/packages`. Страница может дополнительно объявить
иконку.

Пути бэкенда — относительные строки. Демон собирает из них:

```text
/api/plugins/<name>/<path>
/ws/plugins/<name>/<path>
```

Это пространство имён выводится из имени манифеста. Плагин не может занять маршрут другого
плагина или использовать абсолютный путь бэкенда.

## Возможности бэкенда

Необязательный блок backend имеет один из двух видов:

- `exec`: HTTP-маршруты в рамках запроса, каждый указывает одну команду;
- `service`: одна команда переднего плана, взаимодействующая по HTTP/WebSocket через приватный
  Unix-сокет демона, с положительной версией протокола и списком маршрутов. См. [руководство по
  service-бэкендам](service-backend.ru.md) с контрактом дочернего процесса и примерами реализации.

Оба вида могут объявлять имена пакетов и доступ к маршрутам (`session` или `public`). Публичные
HTTP-маршруты ограничены GET и HEAD. `_mndw/*` зарезервирован для протокола готовности и
диагностики демона.

## Проверка

SDK проверяет манифесты с помощью Zod. Демон Go повторяет те же правила. Оба набора тестов
используют общую коллекцию корректных и некорректных фикстур. После запуска валидатора демона
коллекция фиксируется; изменённая фикстура должна обновляться в обоих наборах в одном изменении.

Проверяются:

- наборы символов имени плагина, имени пакета и команды;
- относительные пути без traversal, обратных косых черт и начальных слешей;
- положительные размеры виджета в пределах сетки из двенадцати колонок;
- минимальные размеры, не превышающие предпочтительные;
- дублирующиеся id маршрутов и кортежи маршрутов;
- только HTTP-маршруты exec и требования к протоколу/команде service;
- буквальные аргументы service;
- зарезервированные и некорректные маршруты страниц.

SDK также генерирует `manifest.schema.json` для поддержки редакторов. Неизвестные ключи
манифеста удаляются результатом схемы.

## API контекста

Хост создаёт по одному контексту на экземпляр плагина. Важные поверхности включают хранилище,
информацию о хосте, подписку на тему, injector, overlay и backend.

Клиент бэкенда локально разрешает объявленные id:

```ts
await context.backend?.fetch('stats', {
  query: { host: 'router' },
})

const socket = context.backend?.socket('terminal', {
  protocols: ['tty'],
})
```

Неизвестные id завершаются ошибкой `BackendUnknownId`. Для известной, но неодобренной или
отключённой возможности выдаётся `BackendNotApproved` или `BackendDisabled`. Демон может
вернуть те же ошибки, если состояние изменилось после загрузки дескриптора хостом.

## Фреймворки и общие зависимости

Поддерживаемые фронтенд-фреймворки: vanilla TypeScript, Svelte, Vue и Angular. Зависимости,
предоставляемые хостом, собраны в версионированные общие бандлы:

```text
/shared/<bundle>@<version>.js
```

Таблицей общих зависимостей владеет SDK. Хост, упаковщик CLI и сервер разработки используют
одну и ту же таблицу и import map. `mndw.lock.json` записывает версии, использованные при
сборке плагина. Несовпадения major-версий вызывают предупреждение, но не блокируют загрузку.

Базовый набор общих зависимостей содержит полный пакет `@mndw/ui@0.1.0` и `d3@7.9.0` под
спецификатором `d3`. Поэтому официальные API d3 используют один браузерный модуль и одну
идентичность прототипов. Сторонние расширения, такие как `d3-dag`, остаются упакованными в плагин, пока
отдельное решение об общих зависимостях не добавит их в хост.

В Angular-бандлах действует инвариант идентичности: бандл `angular-core` предоставляет
`@angular/core` и `@angular/core/rxjs-interop` в одном файле, а остальные Angular-бандлы
оставляют `@angular/core` внешним. Исполняемый набор регрессионных тестов защищает это от
дублирования идентичности классов.

## Жизненный цикл и граница доверия

Хост создаёт и удаляет UI-экземпляры. Демон владеет одобрением, доступностью маршрутов, жизненным
циклом процессов бэкенда и контролем доступа. Одобренный shell-бэкенд работает с привилегиями
демона, поэтому одобрение — это граница доверия.

Загруженные плагины с бэкендом остаются в области staging и неисполняемыми до одобрения. После
одобрения демон устанавливает объявленные пакеты, проверяет и подготавливает команды, запускает
совместимые сервисы переднего плана и записывает изменение в состояние. Команды и процессы service по замыслу
работают с привилегиями демона/устройства.
