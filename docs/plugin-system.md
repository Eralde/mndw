# Plugin system

mndw plugins are independently packaged UI modules with an explicit manifest.
The host supplies UI services; `mndwd` supplies controlled backend execution.
The SDK is the contract shared by the host, CLI, and plugin authors.

## Plugin shape

A plugin archive contains a manifest, a frontend entry, and optional backend
assets:

```text
manifest.json
index.js
index.css                 optional
mndw.lock.json            generated by mndw pack
backend/
  main.sh                 optional
```

The entry exports `createInstance`:

```ts
export function createInstance(
  container: HTMLElement,
  context: PluginContext,
): PluginInstance | Promise<PluginInstance>
```

An instance must provide `unmount`. It may provide `onResize`, which receives
the current grid-unit width and height.

## Manifest contract

Every manifest has `manifestVersion: 1`, a path-safe name, semantic version,
`widget` or `page` type, label, and safe relative entry path.

Widgets declare grid-unit dimensions:

```json
{
  "manifestVersion": 1,
  "name": "traffic-widget",
  "version": "1.0.0",
  "type": "widget",
  "label": "Traffic",
  "entry": "index.js",
  "size": { "w": 4, "h": 3, "minW": 2, "minH": 2 }
}
```

Pages declare a single-segment route such as `/traffic`. `/`, `/login`, and
`/settings` are reserved; the host also reserves `/packages`. A page may also
declare an icon.

Backend paths are relative strings. The daemon composes them into:

```text
/api/plugins/<name>/<path>
/ws/plugins/<name>/<path>
```

This namespace is derived from the manifest name. A plugin cannot claim a
different plugin's route or use an absolute backend path.

## Backend capabilities

The optional backend block has one of two kinds:

- `exec`: request-scoped HTTP routes, each pointing at one command;
- `service`: one foreground command speaking HTTP/WebSocket over the daemon's
  private Unix socket, with a positive protocol version and route list. See
  the [service backend guide](service-backend.md) for the child-facing
  contract and implementation examples.

Both kinds may declare package names and route access (`session` or `public`).
Public HTTP routes are limited to GET and HEAD. `_mndw/*` is reserved for the
daemon's readiness and diagnostics protocol.

## Validation

The SDK validates manifests with Zod. The Go daemon mirrors the same rules.
Both suites consume the shared valid and invalid fixture corpus. The corpus is
frozen once the daemon validator starts; a changed fixture must update both
suites in the same change.

Validation covers:

- plugin name, package-name, and command character sets;
- relative paths without traversal, backslashes, or leading slashes;
- positive widget dimensions within the twelve-column grid;
- minimum dimensions no larger than preferred dimensions;
- duplicate route ids and route tuples;
- exec HTTP-only routes and service protocol/command requirements;
- literal service arguments;
- reserved and malformed page routes.

The SDK also generates `manifest.schema.json` for editor support. Unknown
manifest keys are stripped by the schema output.

## Context API

The host creates one context per plugin instance. Important surfaces include
storage, host information, theme subscription, overlay, and backend.

The backend client resolves declared ids locally:

```ts
await context.backend?.fetch('stats', {
  query: { host: 'router' },
})

const socket = context.backend?.socket('terminal', {
  protocols: ['tty'],
})
```

Unknown ids fail as `BackendUnknownId`. A known but unapproved or disabled
capability fails as `BackendNotApproved` or `BackendDisabled`. The daemon can
return the same errors when state changes after the host loaded its descriptor.

## Frameworks and shared dependencies

The supported frontend frameworks are vanilla TypeScript, Svelte, Vue, and
Angular. Host-provided dependencies are built into versioned shared bundles:

```text
/shared/<bundle>@<version>.js
```

The SDK owns the shared-dependency table. The host, CLI packer, and development
server consume that same table and import map. `mndw.lock.json` records the
versions used to build a plugin. Major-version mismatches warn but do not block
loading.

The base shared set includes `@mndw/ui@0.1.5` and the complete `d3@7.9.0`
package under the `d3` specifier. Official d3 APIs therefore share one browser
module and one prototype identity. Third-party extensions such as `d3-dag`
remain plugin-bundled unless a later shared-dependency decision promotes them.

Angular bundles have an identity invariant: the `angular-core` bundle provides
`@angular/core` plus `@angular/core/rxjs-interop` in one file, and the other
Angular bundles keep `@angular/core` external. An executable regression suite
protects this from duplicate class identities.

## Lifecycle and trust boundary

The host creates and removes UI instances. The daemon owns approval, route
availability, backend process lifecycle, and access control. An approved shell
backend runs with the daemon's privileges, so approval is the trust boundary.

Uploaded backend plugins remain staged and non-executable until approval.
After approval, the daemon installs declared packages, validates and stages
commands, starts compatible foreground services, and records the change in
state. Command execution and service processes run with daemon/device
privileges by design.
