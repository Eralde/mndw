# Демон `mndwd`

`mndwd` &mdash; это демон, отвечающий за взаимодействие с устройством и выполнение
бэкендов плагинов. Он предоставляет единый шлюз для команд `exec` и долгоживущих процессов (`service`).

## Топология во время работы

```text
browser
  └─ mndwd
      ├─ static host SPA and plugin assets
      ├─ rci/ and auth/ proxy
      └─ API and WebSocket gateway

mndwd
  ├─ session-gated management
  ├─ declared HTTP and WebSocket routes
  └─ state.json          durable state and audit trail
```

Шлюз получает из единого реестра, построенного по манифестам, плагин, идентификатор маршрута,
транспорт, метод, уровень доступа, статус одобрения и признак включения. Сокеты сервисов, пути
команд, идентификаторы процессов, аргументы и требования к пакетам не попадают в дескрипторы
хоста. Маршрутизация запросов,
порты слушателей и upstream-цели определяются в [`contracts/routing.ru.md`](../contracts/routing.ru.md).

## Загрузка и подтверждение

```text
POST /api/mgmt/upload
  → size and zip checks
  → manifest validation and static command checks
  → staging/<name>/ (non-executable)
  → pending capability summary

POST /api/mgmt/approve
  → explicit package installation
  → move staging into user plugins
  → make declared commands executable
  → mark approved and enabled
```

Активацией сервисов управляет `backend.Runtime`; при старте он согласует одобренные и
включённые сервисы, не повторяя установку пакетов в фоновом режиме. Операции `enable`,
`disable`, `delete`, `restart`, `list` и `pending` завершают управление.

## Бэкенды exec

Маршруты exec принимают только HTTP. Демон буферизует тело запроса до запуска, применяет
ограничения размера и общего числа/числа на плагин, запускает объявленный файл напрямую в
новой группе процессов и уничтожает всю группу по тайм-ауту или отмене. Он передаёт
ограниченные CGI-метаданные, включая `REQUEST_METHOD`, `QUERY_STRING`, `CONTENT_TYPE`,
`CONTENT_LENGTH`, `MNDW_PLUGIN_ID` и `MNDW_ROUTE_ID`; cookies, authorization, CSRF и произвольное
окружение демона не передаются.

Вывод CGI разбирается до фиксации ответа. Запрещённые заголовки (hop-by-hop, CORS,
proxy-credential, `Set-Cookie` и `Content-Length`) удаляются, вывод и stderr ограничиваются,
а ответы получают `Cache-Control: no-store`.

## Состояние бэкенда в реальном времени

`GET /api/plugins/{name}/_mndw/status` — маршрут с авторизацией сессии и
`Cache-Control: no-store`. Аутентификация происходит до разрешения плагина; неизвестные имена
и имена без бэкенда возвращают `404` только после аутентификации. Маршрут отделён от общей
каноникализации путей плагинов, поэтому обычный маршрут манифеста с именем `status` остаётся
допустимым.

Приоритет проекции: `disabled`, `not-approved`, `maintenance`; затем exec возвращает `ready`;
service-бэкенды продолжают проверку статического `incompatible`, структурированного
`blocked` при активации и состояния supervisor. Блокировки активации применяются только к
сервисам, поскольку управляют планированием сервисов; у допуска exec-запросов эквивалентной
блокировки нет.

Состояния service `starting` и `backoff` отображаются как `starting`, а будущее `NextAttemptAt`
округляется вверх до целых секунд. Отсутствующие, равные текущему или истёкшие значения дают
`retryAfterSeconds: null`. `capacity_blocked` отображается как `starting` без подсказки для
повторной попытки; остановленный, неисправный или отсутствующий runtime отображается как
`unavailable`.

Совместимость использует `protocolVersion` манифеста и настроенный список поддерживаемых
протоколов демона независимо от диагностических полей совместимости supervisor. Ответы
содержат только `kind`, `state`, `retryAfterSeconds`, кортежи блокировок или поля
несовместимого протокола. В них никогда нет ошибок, stderr, счётчиков перезапусков, данных
процесса, путей сокетов, учётных данных или токенов.

Привязка имени плагина в SDK — удобное ограничение области, а не средство авторизации.
Любая аутентифицированная сессия устройства может запросить известное имя плагина; конечной
точки для перечисления имён нет. Это раскрытие соответствует существующему уровню доверия
аутентифицированной сессии устройства.

## Service-бэкенды

Авторам плагинов следует использовать [руководство по service-бэкендам](service-backend.ru.md)
для контракта дочернего процесса. На этой странице описаны supervision демона и поведение
безопасности.

Каждый сервис — это процесс переднего плана, взаимодействующий по HTTP/1.1 и, необязательно,
WebSocket через `backend.sock` в `/opt/tmp/mndw/plugin-runtime/<plugin-id>`. Демон управляет
готовностью (`GET /_mndw/ready`), совместимостью протокола, проксированием Unix-сокетов,
lease, группами процессов, задержкой повторного запуска и выключением. Дочерние сервисы
получают `MNDW_BACKEND_SOCKET`, `MNDW_BACKEND_PROTOCOL`, `MNDW_PLUGIN_DATA_DIR` и список
разрешённых переменных окружения.

Состояния runtime: `stopped`, `capacity_blocked`, `starting`, `ready`, `backoff` и `failed`.
Ограничения по умолчанию: 8 общих exec-запросов, 4 на плагин и 8 управляемых сервисов.
Тайм-аут HTTP service — 30 с; drain — 35 с; остановка service — `service-stop-timeout`
(по умолчанию 15 с); финальный reap — 2 с. Неподдерживаемые протоколы остаются включёнными
в состоянии, но не запускаются и сообщают `BACKEND_INCOMPATIBLE`.

## Аутентификация и авторизация

Маршруты управления требуют действующую сессию устройства, а небезопасные изменения
управления также требуют фиксированный заголовок `X-Mndw-Csrf: 1`. Приватные маршруты
плагинов также требуют доступа с сессией; публичный доступ задаётся для каждого маршрута, и
публичными могут быть только HTTP-маршруты GET/HEAD. Публичный доступ не отменяет проверки
одобрения или включённости. `--dev` обходит проверку сессии, но не обходится CSRF для небезопасных изменений
управления.

Origin WebSocket-соединения проверяется на шлюзе. Заголовки CORS не выдаются, а фиксированный заголовок
`X-Mndw-Csrf: 1` обязателен для небезопасных приватных HTTP-запросов и вызовов управления.
Обслуживание закрывает сокеты кодом WebSocket `1012` и причиной `mndw updating`; клиенты
показывают явный интерфейс переподключения и не возобновляют соединение молча.

## Диагностика, состояние и граница доверия

Экспорт диагностики объединяет состояние демона с необязательным JSON
`GET /_mndw/diagnostics` готового service. Ответы имеют короткий тайм-аут, ограничены для
каждого плагина и в сумме, рекурсивно очищаются и обрабатываются независимо для каждого
сервиса; отдельный файл диагностики в файловой системе не нужен. Команды, аргументы, сокеты,
PID, учётные данные, cookies и окружение дочерних процессов не попадают в отчёты. Постоянное
состояние находится в `/opt/var/lib/mndw`; runtime-сокеты, lease и временное состояние — в
`/opt/tmp/mndw/plugin-runtime` с режимом `0700`.

Одобренные команды exec и дочерние сервисы по замыслу работают с привилегиями демона/устройства.
Поэтому одобрение — это граница выполнения кода с правами, эквивалентными root.
