# Владение маршрутами во время работы

Этот документ фиксирует владение маршрутами. Пути — это публичная часть протокола;
детали реализации остаются внутри среды выполнения, которой они принадлежат.

| Route | Production owner | Development owner | Responsibility |
| --- | --- | --- | --- |
| `/api/**` | `mndwd` | Vite proxy to `mndwd` | Управление, диагностика, палитра и HTTP-диспетчеризация плагинов |
| `/api/plugins/<name>/**` | Диспетчеризация `mndwd` | `mndwd` через прокси Vite | Конечные точки бэкендов одобренных/включённых плагинов |
| `/api/mgmt/**` | `mndwd` | `mndwd` через прокси Vite | Загрузка, одобрение, жизненный цикл, opkg и чтение данных управления |
| `/api/mndw/**` | `mndwd` | `mndwd` через прокси Vite | Доступ к устройству и API постоянных RCI-сессий |
| `/ws/**` | `mndwd` | Прокси Vite на `mndwd` | WebSocket-прокси бэкендов плагинов |
| `/plugins/<name>/**` | Статический frontend `mndwd` | Статическое middleware плагинов Vite | Ресурсы встроенных плагинов |
| `/user-plugins/<name>/**` | Статический alias `mndwd` | Статическое middleware плагинов Vite | Ресурсы одобренных пользовательских плагинов |
| `/shared/<bundle>@<version>.js` | Статический frontend `mndwd` | Middleware общих бандлов Vite | Предоставленные хостом общие JavaScript-бандлы и цели import map |
| `/rci/**` | Внутрипроцессный прокси устройства в `mndwd` | Прокси устройства в Vite | RCI API сетевого устройства; прозрачная передача |
| `/ci/**` | Внутрипроцессный прокси устройства в `mndwd` | Не проксируется и не предоставляется Vite | CI API сетевого устройства; прозрачная передача |
| `/auth/**` | Внутрипроцессный прокси устройства в `mndwd` | Прокси устройства в Vite | API аутентификации сетевого устройства и upstream-проверка сессии |

## Слушатели и upstream-цели

Факты о production-слушателе и upstream:

- `mndwd` владеет единственным LAN-слушателем, доступным браузеру, для статических файлов,
  прокси устройства, API и WebSocket-маршрутов. Режим front door включается через `--frontend-dir`.
- Порт front door по умолчанию — `1189`. Сначала `mndwd` пытается использовать сохранённый
  порт, затем начальное значение из миграции, затем `1189`, а после этого оставшиеся порты
  `1190..1289` по возрастанию.
- Выбранный порт атомарно сохраняется в `/opt/var/lib/mndw/frontend-port`. При однократном
  обновлении, на время перехода, `/opt/var/lib/mndw/lighttpd-port` служит начальным значением
  для миграции и удаляется после успешного запуска front door. `lighttpd-port-policy` упразднён.
- `--frontend-listen` по умолчанию равен `0.0.0.0` и намеренно привязывается только к IPv4 для
  совместимости с прежним слушателем устройства. Обслуживание IPv6 не предусмотрено.
- `S70mndwd` обнаруживает HTTP-слушатель устройства `/auth` среди локальных TCP-слушателей по
  challenge `WWW-Authenticate: x-ndw2-interactive` / `x-ndw4-interactive`; совпавший URL
  передаётся `mndwd` для проверки сессии и проксирования устройства.
- `MNDW_DEVICE_PORT` в `/opt/etc/mndw.conf` переопределяет обнаружение, когда устройство
  предоставляет несколько подходящих слушателей. Если подходящего слушателя нет или их больше
  одного, обнаружение завершается безопасным отказом.
- Upstream для проверки сессии устройства в автономном `mndwd` по-прежнему по умолчанию равен
  `http://127.0.0.1:80`; init-скрипт пакета передаёт обнаруженный URL устройства.

Пакет mndw больше не зависит от lighttpd и не настраивает его. При обновлении `postinst`
удаляет устаревшие runtime-артефакты lighttpd, принадлежащие mndw, выводит однократное
уведомление об удалении только для старого маркера владения mndw и запускает новый front
door. При неудачном перезапуске `lighttpd-port` сохраняется для повторной попытки.

Цели прокси в режиме разработки настраиваются в `frontend/host/vite.config.ts`: `/api` и `/ws` используют
`MNDW_DAEMON` (по умолчанию `http://127.0.0.1:9090`), а `/rci` и `/auth` — `MNDW_HOST_DEVICE`.
Задайте `MNDW_HOST_DEVICE` как полный URL устройства, например `http://192.168.1.1`, а не как
простой IP-адрес.

Правила владения:

- `mndwd` владеет каждым доступным браузеру production-маршрутом, включая статические файлы,
  прокси устройства, `/api` и `/ws`; состояние возможностей плагина за пределами реестра,
  выведенного из манифестов, он не определяет.
- Хост владеет загрузкой в браузере и прокси в режиме разработки; он не становится источником
  истины о состоянии демона.
- Пакеты плагинов владеют объявленными payload бэкенда и статическими ресурсами, но не
  общей политикой маршрутов или approval.
- URL общих бандлов используют `/shared/<bundle>@<version>.js`; таблица бандлов и версий
  берётся из `frontend/sdk/shared-dependencies.ts` и отражается в
  `contracts/protocol/shared-deps.json`.
