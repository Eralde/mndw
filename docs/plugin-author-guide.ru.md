# Руководство автора плагинов

[English](plugin-author-guide.md) | **Русский**

Это руководство описывает минимально полезный плагин и проверки, которые он должен пройти.
Используйте CLI для создания каркаса и упаковки, чтобы сгенерированные файлы соответствовали
контрактам хоста и демона.

## Создайте проект

```bash
mndw create hello --type widget --framework svelte --backend sh
cd hello
mndw dev .
```

Для страницы используйте `--type page` и выберите незарезервированный маршрут. Для vanilla-
плагина используйте `--framework vanilla`. Vue и Angular используют те же контракты манифеста
и жизненного цикла, но добавляют специфичные для фреймворка общие бандлы. Зарезервированные
маршруты страниц: `/`, `/login`, `/packages`, `/packages/services` и `/settings`.

Структура сгенерированного проекта:

```text
hello/
  manifest.json
  src/index.ts
  src/App.svelte       Svelte projects only
  src/index.css
  backend/main.sh      when --backend sh is selected
```

Плагины могут хранить поведение только для разработки в `src/index.ts`, который загружает
`mndw dev`. Чтобы выбрать другой production-исходник, добавьте настройку только для сборки
в `package.json`:

```json
"mndw": {"productionEntry": "src/index.prod.ts"}
```

`mndw pack` собирает только настроенный production-исходник; entry манифеста и имя файла
результата не меняются. Настроенный файл должен быть обычным `.ts` внутри `src/`, а
`src/index.ts` всё равно должен существовать: он нужен `mndw validate`, и `mndw dev` загружает
его по пути.

На уровне репозитория `pnpm dev` собирает встроенные плагины из `src/index.ts`, а
`pnpm build-builtin-plugins` использует настроенные production entry.

Примеры, предназначенные для загрузки, находятся в `plugins/examples` и собираются командой
`pnpm build-example-plugins`.

## Реализуйте модуль

Entry экспортирует `createInstance`. Смонтируйте UI в переданный контейнер и верните экземпляр
с очисткой:

```ts
export const createInstance = (
  container: HTMLElement,
  context: PluginContext,
): PluginInstance => {
  container.textContent = `Hello ${context.hostInfo.deviceName}`

  return {
    unmount: () => {
      container.replaceChildren()
    },
  }
}
```

Используйте `onResize({w, h})`, когда изменение раскладки влияет на отрисовку. `w` и `h` —
единицы сетки, а не пиксели. Предпочтительный и минимальный размеры виджета задаются в объекте
`size` манифеста.

## Правила манифеста

Имена — строчные безопасные для пути сегменты. Пути entry и исходников бэкенда относительные;
они не могут содержать traversal или обратные косые черты. Маршруты страниц состоят из одного
сегмента и не могут использовать `/`, `/login` или `/settings`; хост дополнительно резервирует
`/packages`.

Бэкенд exec объявляет команды непосредственно в HTTP-маршрутах:

```json
{
  "manifestVersion": 1,
  "backend": {
    "kind": "exec",
    "routes": [{
      "id": "hello",
      "transport": "http",
      "method": "GET",
      "path": "hello",
      "command": "backend/main.sh"
    }]
  }
}
```

Путь — `hello`, а не `/api/plugins/hello/hello`. Пространство имён плагина добавляет `mndwd`.

## Реализуйте service-бэкенд

Для постоянного HTTP/WebSocket-бэкенда следуйте [руководству по service-бэкендам](service-backend.ru.md).
В нём описаны манифест, контракт Unix-сокета/готовности, жизненный цикл, граница безопасности
и проверенный эталон на Go.

## Вызовите бэкенд

Используйте объявленный id, а не URL, собранный вручную:

```ts
const response = await context.backend?.fetch('hello')
const text = await response?.text()
```

Для WebSocket используйте `context.backend.socket('terminal')`. SDK сообщает об неизвестных,
неодобренных и отключённых возможностях типизированными ошибками. Обрабатывайте эти ошибки в
тексте интерфейса, не полагаясь на детали URL демона.

## Напишите shell endpoint

Shell-скрипт получает метаданные запроса через переменные окружения, а тело запроса — через
standard input. Он записывает ответ в формате CGI:

```sh
#!/bin/sh

printf 'Status: 200 OK\r\n'
printf 'Content-Type: text/plain\r\n'
printf '\r\n'
printf 'hello from %s\n' "$MNDW_PLUGIN_ID"
```

Объявите каждую исполняемую команду в манифесте. `mndw pack` копирует объявленные команды с
режимом `0755`, отклоняет отсутствующие файлы и включает их в архив.

## Используйте сервисы хоста

Предпочитайте поверхности SDK и контекста:

- `storage` — состояние одного экземпляра виджета;
- `sharedStorage` — состояние, общее для экземпляров одного плагина;
- `rciManager` — обмен данными с устройством;
- `hostInfo` — идентификатор устройства и тема;
- `overlay` — модальный диалог, drawer, popover или другой UI верхнего слоя. При ширине viewport
  `<=600px` отображаемые хостом модальные окна и drawer превращаются в полноширинные нижние
  sheets размером по содержимому; их явные параметры `width` и `height` игнорируются, а выбор
  представления делается при открытии overlay;
- `onThemeChange` — отрисовка с учётом темы;
- `injector` — одобренные токены сервисов хоста.

Не подключайте глобальные overlay, глобальные обработчики событий или управление фокусом на
уровне документа без очистки. Хост владеет верхним слоем и вызывает `unmount`.

## Соблюдайте единый стиль

Используйте сгенерированные дизайн-токены `--mndw-*` из SDK. Хост поддерживает светлую и
тёмную темы, и каждый пример плагина должен оставаться читаемым в обеих. По возможности
ограничивайте CSS плагина корнем плагина.

## Проверьте и упакуйте

Перед загрузкой выполните полный цикл автора:

```bash
mndw validate .
mndw pack .
mndw zip .
```

Проверьте, что архив содержит в корне `manifest.json`, результат entry, необязательный
`index.css`, `mndw.lock.json` и все объявленные ресурсы бэкенда.

Во время approval бэкенд-плагины показывают id маршрута, method/path и протоколы WebSocket.
Считайте approval проверкой безопасности: одобренные команды exec и дочерние service
выполняются с привилегиями устройства демона.
